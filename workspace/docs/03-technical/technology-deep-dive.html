Supabase — PostgreSQL + Auth + RLS + Real-time
Open-source Firebase alternative. PostgreSQL 15 database + phone OTP auth + Row Level Security + real-time subscriptions + storage. Ek platform pe sab kuch — zero configuration.
✓ Chosen Free 500MB 50K users free ACID transactions
Kyun PostgreSQL — not NoSQL
Financial data = relational by nature: User → Portfolio → Holdings → Analysis → Subscription. These relationships have foreign key constraints. Ye ensure karta hai orphaned data nahi banta — payment without user, analysis without portfolio.
ACID Transactions: Atomicity — "INSERT payment + UPDATE tier = either both happen or neither." Without ACID: payment record inserted, tier update fails = user paid but didn't get access. Ye fintech mein catastrophic bug hai.
XIRR needs exact dates: PostgreSQL DATE type exact storage. MongoDB BSON dates can have timezone offset issues causing XIRR to be off by 0.1–0.5% due to date boundary errors.
SQL for analytics: "Which portfolios have overlap >60%?" = one SQL query. In MongoDB this requires complex aggregation pipeline. Business analytics easy hota hai PostgreSQL mein.
Row Level Security (RLS): Policy: auth.uid() = user_id. Even if backend code bug ho — database policy block karegi. Double security layer. DPDPA compliance automatic.
Free tier: 500MB database, 50K MAU, 2GB bandwidth, 500MB storage. MVP ke liye 10,000 users tak completely free.

import pdfplumber, re
from fuzzywuzzy import process

def parse_cas(pdf_path, all_funds):
    with pdfplumber.open(pdf_path) as pdf:
        text = "".join(p.extract_text() for p in pdf.pages)
    # Match fund names to AMFI codes
    funds = re.findall(r'([A-Z].{15,60})\s+([\d,]+\.\d{2})', text)
    return [(process.extractOne(f, all_funds), amt) for f, amt in funds]

F1 — XIRR: Extended Internal Rate of Return
SciPy brentq Newton-Raphson solver. 6-decimal precision. Handles irregular SIP cashflows correctly. "11.5364%" not "approximately 11–13%".
Why XIRR — not CAGR or simple returns
XIRR — solves for r
Σ CF_i / (1 + r)^(days_i / 365) = 0
CF_i = each SIP investment (negative) + current portfolio value (positive). days_i = days since first cashflow. r = XIRR rate. brentq finds r where NPV = 0.
CAGR assumes lump sum. Indian investors do SIPs. Rs 5K/month SIP for 3 years, CAGR says 14%, XIRR correctly says 11.2%. Wrong XIRR = wrong goal gap calculation = wrong advice.
Per-fund XIRR (Advanced): "HDFC Flexicap XIRR: 8.2% vs Parag Parikh XIRR: 16.4%." Direct comparison showing which specific fund is underperforming. Much more actionable than portfolio-level XIRR only.
Exact code
Pythoncalculations/xirr.py
from scipy.optimize import brentq
from datetime import date

def calculate_xirr(holdings: list) -> float:
    cfs, dates = [], []
    today = date.today()
    for h in holdings:
        cfs.append(-h['invested_amount'])
        dates.append(h['purchase_date'])
    cfs.append(sum(h['current_value'] for h in holdings))
    dates.append(today)
    d0 = min(dates)
    days = [(d-d0).days for d in dates]
    def npv(r):
        return sum(c/((1+r)**(d/365)) for c,d in zip(cfs,days))
    try:
        return round(brentq(npv,-.99,10,xtol=1e-8)*100,4)
    except: return 0.0
Why scipy.brentq (not other solvers)
Newton-Raphson (simple): Can diverge if starting guess far from solution. Naxance ke typical XIRR range (-99% to +1000%) mein divergence possible.
brentq (chosen): Combines bisection + secant method. Guaranteed convergence when function changes sign in [a,b]. xtol=1e-8 = 8 decimal places.
pyxirr library: Rust-based, 10x faster than Python. Drop-in replacement: from pyxirr import xirr. Phase 2 upgrade when speed matters at scale.
numpy_financial.irr: Less accurate for irregular cashflows. Not recommended for Nxance's exact-math requirement.

F2 + F3 + F4 — Sharpe/Alpha/Beta · CVaR · Jaccard Overlap
Three frameworks, one card. Risk-adjusted returns vs Nifty 50. Worst-case loss probability. Fund duplication detection in exact Rs.
F2 — Quant metrics explained
Sharpe Ratio
(Rp − Rf) / σp × √252
Rp=portfolio return, Rf=6.5% (RBI repo), σp=daily std dev annualized. >1=good, >2=excellent. Penalizes total volatility.
Jensen Alpha (most actionable)
α = Rp − [Rf + β(Rm − Rf)]
Rm=Nifty 50 return (yfinance). α>0=outperforms CAPM prediction. α×corpus=Rs opportunity cost/year.
Sortino Ratio: Like Sharpe but only penalizes downside volatility. More relevant for equity MFs where upside volatility is good. Higher Sortino = better downside protection per unit of return.
F3 — CVaR Risk Analysis
F3 — CVaR Parametric
CVaR = μ − σ·φ(Φ⁻¹(α)) / (1−α)
α=0.05 (95% confidence). μ=mean daily return, σ=std dev. "In worst 5% of months, portfolio drops ≥CVaR%." Applied to 2008 (−52%) and 2020 (−38%) crash scenarios.
Pythoncalculations/risk.py
from scipy import stats
import numpy as np

def calculate_cvar(holdings, nav_data, alpha=0.05):
    returns = portfolio_daily_returns(holdings, nav_data)
    mu  = np.mean(returns)
    sig = np.std(returns)
    # Parametric CVaR
    cvar = -(mu - sig * stats.norm.pdf(
        stats.norm.ppf(alpha)) / alpha)
    annual_cvar = cvar * np.sqrt(252)
    # Crisis simulation
    crash_2008 = sum(h['current_value'] for h in holdings) * 0.52
    return {'cvar_95':round(annual_cvar*100,1),
            'crash_2008_loss_rs':round(crash_2008,0)}
F4 — Jaccard Overlap + TER Waste
F4 — Jaccard Similarity + TER Waste
J = |A ∩ B| / |A ∪ B| waste_rs = J × avg_TER × corpus
A=Fund1 top-10 stocks, B=Fund2 top-10 stocks. J=0.72 → 72% overlap → Rs waste = 0.72 × 1.5% × corpus = exact Rs/year shown as "Issue #1" on free tier.
Pythoncalculations/overlap.py
async def calculate_overlap(holdings, fh_data):
    fstocks = {}
    for h in holdings:
        code = h['scheme_code']
        fstocks[code] = {
            item['name'].upper()
            for item in fh_data.get(code, [])
        }
    codes = list(fstocks)
    max_j = 0
    for i in range(len(codes)):
        for j in range(i+1, len(codes)):
            a,b = fstocks[codes[i]], fstocks[codes[j]]
            u = len(a|b)
            jv = len(a&b)/u if u>0 else 0
            max_j = max(max_j, jv)
    corpus = sum(h['invested_amount'] for h in holdings)
    return {'jaccard_pct':round(max_j*100,1),
            'ter_waste_rs':round(max_j*0.015*corpus,0)}

F5 — Portfolio construction analysis
HHI Concentration Index
HHI = Σ (weight_i)²
HHI=1 → single fund (max risk). HHI=1/n → equal weight (optimal). HHI>0.5 → over-concentrated. "70% in one fund = risky for your goal."
BHB Attribution: Brinson-Hood-Beebower model. Separates return into: asset allocation effect (equity/debt ratio choice) + selection effect (which funds within asset class). Shows "your asset allocation added 2.1% but fund selection subtracted 3.4% — bad fund choice is your main problem."
Regular vs Direct plan detector: scheme_name.contains("Regular") → instant issue: "Switch to Direct plan of same fund → save Rs exact_amount/year." Phase 1 quick win.
F6 — Goal alignment gap
F6 — Annual Goal Gap
gap_rs = (exp_XIRR − act_XIRR) × corpus
exp_XIRR from MCQ Q3 answer. act_XIRR from brentq. Example: (12% − 9.2%) × 5,00,000 = Rs 14,000/year missed.
Timeline impact: "At 9.2%, you'll reach Rs 1Cr goal in 22 years. After fixes at 14.8%: 16 years. You save 6 years of your life." This framing converts users far more than Rs amount alone.
Advanced — Monte Carlo (Phase 2): 10,000 simulations with actual volatility. "Probability of reaching Rs 1Cr by 2040: 34% now → 67% after fixes." Probability framing is most powerful conversion trigger discovered in financial products.

import hmac, hashlib, json, os

@router.post("/payment/webhook")
async def webhook(request: Request):
    body = await request.body()
    sig  = request.headers.get("x-razorpay-signature")
    
    # HMAC-SHA256 verify
    secret = os.environ["RAZORPAY_WEBHOOK_SECRET"]
    exp = hmac.new(secret.encode(), body, hashlib.sha256).hexdigest()
    if not hmac.compare_digest(exp, sig):
        raise HTTPException(401)
    # compare_digest = timing-attack proof
    # Regular == vulnerable: attacker measures time
    # → guesses signature byte by byte
    
    event = json.loads(body)
    if event.get("event") == "payment.captured":
        pay = event["payload"]["payment"]["entity"]
        uid = pay["notes"].get("user_id")
        if uid: await activate_subscription(pay["order_id"], uid)
    return {"status": "ok"}

5-Layer Security Stack
JWT auth · HMAC webhooks · HTTPS/TLS · Cloudflare DDoS · Redis rate limiting. Financial app = highest security standard required from Day 1.
Layer 1 + 2: JWT + HMAC explained
JWT (JSON Web Token): Supabase OTP login → signed JWT token → sent in Authorization: Bearer header → FastAPI decodes with SUPABASE_JWT_SECRET → user_id extracted. Stateless — no session storage needed.
HS256 (Phase 1): Symmetric key. Supabase + Railway share same secret. Simple, fast, adequate for single-server architecture.
RS256 (Phase 2 upgrade): Asymmetric. Private key signs (API server only), public key verifies (NxanceLM server, any microservice). Even if NxanceLM server is compromised, tokens cannot be forged. Multi-server security.
