Rolling Return — return over every rolling N-year window, not one flattering stretch.
Alpha over Benchmark — excess return vs the fund's true benchmark, after fees.
Consistency of Alpha — % of rolling windows where alpha stayed positive — steady beats lumpy.
Sharpe / Sortino — risk-adjusted return; Sortino punishes only downside.
Standard Deviation — annualised volatility — the fund's own bumpiness.
Max Drawdown — worst peak-to-trough fall the holder had to sit through.
Expense Ratio — annual cost drag; Direct-vs-Regular gap flagged in ₹.
Downside Capture — how much of the market's fall the fund catches — lower is better.
Upside Capture — how much of the market's rise the fund catches — higher is better.

3 · Health-Check Pipeline
The Full Health-Check Pipeline — Read → Macro → Select → Engines → Backtest → Report
Every run follows this exact order. The backtest is a hard gate — nothing reaches the user unless the result is verified correct and proven to fulfil the user's expectation.
STEP 1 · READ & UNDERSTAND
Read the uploaded portfolio + the questionnaire
The engine reads what the user holds (every instrument, quantity, buy date, cost) and what they expect — goal, amount, timeline, true risk tolerance from their answers. Nothing is judged yet: this builds the complete has-vs-needs picture.
↓
STEP 2 · MACRO ANALYSIS · STAGE 1
Macro-analyse every held asset vs the user's expectation
Each bought instrument runs through the 15 macro parameters. The question: is this asset even the right kind of asset for this user's stated expectation — right class, right risk, right for the timeline?
↓
STEP 3 · SELECTION · STAGE 2
Find the best alternative — 16 layers, per-asset-class parameters
For every weak/mismatched holding, the Selection Engine runs all 16 layers graded on the parameter pack for that asset's class (above), producing the best alternative and the quantity that moves the user toward the goal.
↓
STEP 4 · ALL OTHER ENGINES
Every other sub-engine adds its part
Risk, Correlation, Forecasting (Monte-Carlo goal probability), Crisis/backtest data, Tax, Behaviour, Peer-Intelligence and Number-Guard each contribute — so the report is complete: exact gap in ₹, goal-probability lift, risk-fit, cost leak.
↓
STEP 5 · BACKTEST · THE GATE
Backtest the report & alternatives before anything reaches the user
The whole report is backtested: is the analysis correct, and would the alternatives have fulfilled the user's expectation across real history + the 5-crash stress set? PASS → report. FAIL → loop to Step 3. Nothing that fails is ever shown.
↓
STEP 6 · REPORT TO USER
Deliver the plain-language report
Only on PASS: the report states what is wrong, the main reason it exists, the best alternative, the quantity, and exactly why this one was chosen — in language a retail investor understands.
4 · Construction Pipeline
The Full Construction Pipeline — Questionnaire → Analyse → Blueprint → Select → Engines → Backtest → Execute
Every run follows this exact order. The backtest is a hard gate — nothing reaches the user unless the result is verified correct and proven to fulfil the user's expectation.
STEP 1 · QUESTIONNAIRE
User answers the questionnaire
Goal, amount, timeline, real risk tolerance, constraints — the raw input for everything below.
↓
STEP 2 · ANALYSE THE USER
Work out what portfolio this user needs
The Analysis engine derives what kind of portfolio this user needs, the required XIRR, and the constraints — defining the target the whole build must hit.
↓
STEP 3 · BLUEPRINT · STAGE 1
Decide the % split across asset classes
Using the macro parameters against the user's expectation, the engine sets the diversified blueprint: how much % to stocks, MF, FD, gold, commodities, currency — a genuinely diversified mix for this user.
↓
STEP 4 · SELECTION · STAGE 1 → STAGE 2
Pick the specific instruments and their quantity
The Selection Engine first filters with the overall macro parameters, then enters each class and uses the per-asset-class parameters to choose the specific instrument and decide quantity — e.g. inside equity, exactly which stocks/funds and how many units.
↓
STEP 5 · ALL OTHER ENGINES
Shape the best diversified portfolio
Correlation (so slots don't secretly overlap), Risk, Forecasting, Crisis/backtest, Tax and Behaviour all contribute to make the blend optimal, not just a list of individually-good names.
↓
STEP 6 · BACKTEST · THE GATE
Backtest the built portfolio vs the user's expectation
The finished portfolio is backtested across real history + the 5-crash set. PASS → send to user. FAIL → rebuild loop. Nothing that fails is shown.
↓
STEP 7 · SEND + EXPLAIN → EXECUTE
User reviews, with a reason for every number
On PASS, the portfolio goes to the user with a detailed explanation: why this much amount in this asset, why this instrument. The user can change anything — any change restarts the whole pipeline (re-analyse → re-select → re-backtest). If happy, they execute.
The Backend Number System — Everything Becomes a Score
To keep all of this fast and objective, the engine turns every single thing into a number behind the scenes. Every parameter, every layer, every instrument gets a score; the engine simply picks the highest-scoring options when analysing the portfolio. This is 100% backend — the user never sees raw numbers, only the plain-language result and its reason.
HOW SCORING WORKS (HIDDEN)
1 · Each macro parameter scores every asset 0–100 (Stage 1).
2 · Each per-asset-class parameter scores every instrument 0–100 within its own category (Stage 2, z-scored).
3 · Layers combine into one FIT score per instrument (weighted per class).
4 · The Fraud gate can zero out any score (hard veto).
5 · The engine ranks by score, picks the best; quantity is a second scored pass (correlation + behaviour trim).
6 · The whole result gets a backtest score — the pass/fail gate before the user sees anything.
USER SEES vs BACKEND DOES
Backend (hidden): hundreds of 0–100 parameter scores, FIT scores, correlation matrices, rank tables, backtest scores — pure math in the Rust/Python core.
Front-end (shown): only the outcome in plain language — "this holding drags you down because X; the better fit is Y; here's how much; here's why." No raw scores, no formulas on screen.
Score every paramk → sk∈[0,100] · z=(x−μcat)/σcat→100·Φ(z)
FITinstrument=Σk wk·sk · fraud fail → FIT=0 (hard veto)
Choose=argmax(FIT) per slot · Quantity=f(FIT, correlation, behaviour)
Backtest=PASS if accuracy≥θ AND expectation-fulfilled≥θ, else loop
The rule (Number Guard): the Rust/Python core computes every score; NxanceLM can explain any number in words but computes none. Scores drive the decision; language delivers it; the raw number system stays hidden from the user.

Section 01 — Overview

Not a bolt-on chatbot, and not one monolithic model. NxanceLM is Nxance's own AI, built from scratch, made of 14 mini-engines that together form a proper intelligence. It does four things: (1) works inside Construction and Health Check as a helper, (2) generates every report card and explanation, (3) tracks user behaviour to feed both engines, and (4) answers finance/economy questions in chat. The core rule that governs all of it: it never decides alone — it helps the real engines and the user, and it serves the one locked motive.

Section 02 — Architecture

The 5 Layers — How 18+ Mini-Engines Fit Together

A query flows down through five layers. Each mini-engine has one job; together they behave like a single intelligence. This is why "mini-engines" and not "one model" — each part is independently buildable, testable, and upgradable, exactly like the sub-engine philosophy in Construction and Health Check.

1 · PERCEPTION
Mini 01–02. Understands what the user actually asked and turns text into tokens the model reads — using NxanceLM's own tokenizer, not a borrowed one.
2 · KNOWLEDGE
Mini 03, 14. Retrieves the right facts (RAG over live engine data + finance corpus) and remembers the conversation across sessions.
3 · REASONING CORE
Mini 04, 05, 09. The actual intelligence — the hybrid from-scratch model, plus research/analysis and behaviour tracking.
4 · GENERATION
Mini 06, 07, 08, 10. Turns reasoning into the actual output — explanations, report cards, chat answers, daily digests.
5 · GUARD
Mini 11, 12, 13. Wraps everything — verifies every number, enforces boundaries (helper not decider), and accelerates the heavy sub-problems with quantum.
WHY 14, NOT 1
Same reason Construction has 22 sub-engines: many specialised parts, each independently improvable, converging on a better answer than one black box.
Key mental model: the Reasoning Core (Mini-04) is the "brain," but a brain alone isn't useful. Perception feeds it clean input, Knowledge feeds it facts, Generation gives it a mouth, and the Guard layer keeps it honest and safe. Remove any layer and the AI breaks — which is exactly why it's built as coordinated mini-engines.

Section 04 — The Rule Above All Rules

The Golden Rule — Helper, Never a Lone Decider

This is the one constraint that no mini-engine and no future upgrade is ever allowed to break. It's what makes NxanceLM trustworthy in a finance product.

🤝 Inside the Engines — One Parameter Among Many
When NxanceLM works inside Construction or Health Check, it is a sub-engine and a parameter, weighted like any other — for example, one scoring layer of Selection's 16. It can flag, adjust, and explain. It cannot override the collective verdict, cannot bypass the Fraud Gate, and cannot execute anything. The pipeline order is fixed: all engines and parameters run first → everything is checked → then one collective best decision is produced. NxanceLM is a voice at the table, never the chair.
💬 In Chat — Research & Answer, Then Redirect
In free chat, NxanceLM researches and answers finance/economy questions fully. But when a user asks it to "build me a portfolio" or "analyse my portfolio," it doesn't try to do that itself in chat — it says: "use the Construction / Health Check option in the app — those give you the best, fully-analysed answer." Because a proper build/analysis needs all 22 sub-engines and quantum optimisation, not a single chat response. The chat knows its own limits and points to the real tools.
⚖️ Why this rule exists — and why it's permanent
A single AI confidently deciding your money is exactly the thing that goes catastrophically wrong. Nxance's entire trust model is that no single component — not even the AI — decides alone. Using many engines and parameters has one purpose: the final answer survives dozens of independent checks, not one model's opinion. Removing this rule to make NxanceLM "more powerful" or "more decisive" would be a trust regression, not an upgrade — no matter how good the model gets. It is architecture, not policy.
Section 05 — Perception & Reasoning Core

Mini-Engines 01–04 — Understanding & Thinking

The first four mini-engines take a raw query and turn it into understood, tokenised input, then run it through the actual from-scratch intelligence. Everything else in NxanceLM depends on these getting it right.

👂 MINI-01 · Intent & Understanding Engine PERCEPTION
What it does
Reads the user's message and works out what they actually want — is this a portfolio-build request, an analysis request, a factual economy question, a "why did you recommend this" explanation request, or casual chat? This routing decision determines everything downstream.
Why it's first
A "build me a portfolio" message must be redirected to the Construction engine, not answered in chat (Golden Rule). Mini-01 is the engine that detects that intent and routes correctly — answer here, or point to the right app tool.
Handles Hinglish
Trained to understand mixed Hindi-English ("mera portfolio theek hai kya?") natively — intent detection works across code-switched language, which most off-the-shelf models handle poorly.
🔤 MINI-02 · Tokenizer & Encoder PERCEPTION
What it does
Converts text into tokens the model reads — using NxanceLM's own custom BPE tokenizer (32k vocabulary, written in Rust), built specifically to preserve AMFI scheme codes, Hinglish tokens, and ₹ formatting as single meaningful units.
Why own, not borrowed
GPT/Llama tokenizers split "₹1,50,000" or "HDFC Top 100 Direct Growth" into clumsy fragments, wasting context and losing meaning. A finance-native tokenizer keeps these intact — better accuracy and cheaper compute per query. This is step one of "built from scratch."
# Own tokenizer — trained on OUR corpus, not reused
tokenizer = NxanceTokenizer.train(
    corpus_path="data/nxance_corpus/",
    vocab_size=32000,
    special_tokens=["<AMFI_CODE>", "<RS_AMOUNT>", "<HINGLISH>"]
)  # preserves ₹ amounts, scheme codes, Hinglish as single tokens
📚 MINI-03 · Knowledge & Retrieval Engine (RAG) KNOWLEDGE
What it does
Before the model answers, this engine retrieves the relevant facts — from the live engine outputs (this user's actual numbers), the finance knowledge base (SEBI rules, fund data, macro), and market data. The model then reasons over retrieved facts, not just its training memory.
Why RAG matters here
Markets change daily; a model's frozen training data goes stale. RAG lets NxanceLM answer with today's NAVs, this user's real holdings, and current policy — grounding every answer in verifiable data instead of hallucinated recall. This is what makes finance answers trustworthy.

A vector database (Qdrant / pgvector) over the Data Intelligence store shared with both engines, plus live market-data adapters.
🧠 MINI-04 · Reasoning Core — The Actual Intelligence REASONING CORE
The architecture
A hybrid Transformer + Mamba (SSM) + Mixture-of-Experts model, trained 100% from scratch. Three ingredients, each for a reason:
Transformer (Attention)Holds exact-number precision — critical when a single wrong digit in a ₹ figure destroys trust. Attention is unbeaten at precise, local reasoning.
Mamba (SSM)Holds long historical context cheaply — years of a user's transaction history, decades of market data — where pure attention would be too expensive.
Mixture-of-ExpertsTrillion-scale capacity at a fraction of the compute — only the relevant expert subset activates per query (sparse routing), so full knowledge, cheap inference.
Why this specific hybrid: a finance AI needs three things at once — exact numbers (Attention), long memory (Mamba), and huge knowledge without huge cost (MoE). No single classic architecture gives all three, so NxanceLM combines them. This is a genuine architectural decision, not a copy of any existing open model's config.

Section 11B — The AI Quant Core

Formulas of the Model Itself — Transformer to Trillion Parameters

The Construction and Health Check documents carry the finance math; this page carries the math of the AI itself — the exact equations Raghav will implement to build NxanceLM from scratch, and the honest engineering behind the trillion-parameter claim.

🧠 A · The Transformer Core (Mini-04's substrate)
A1 · Attention — the one equation the whole model is built on
Attention(Q,K,V) = softmax( QKᵀ / √dk ) · V
Q,K,V = query/key/value projections of the token embeddings  ·  dk = key dimension (the √dk keeps gradients stable). Multi-head: run h attention heads in parallel on d/h-dim slices, concatenate, project — MultiHead = Concat(head₁…head_h)·Wᴼ. Production choices: RoPE positional encoding, grouped-query attention (GQA) for cheap inference, SwiGLU feed-forward, RMSNorm.
A2 · Parameter count — where the size actually lives
P ≈ 12 · L · d²   (L layers, hidden size d; embeddings add V·d)
Example: L=32, d=4096 → ≈6.4B params (a Llama-7B-class model). Training compute: FLOPs ≈ 6·P·N for N training tokens — this formula is how the GPU budget in the Cost section is derived, not guessed.
🎓 B · Training Math (the from-scratch phase)
B1 · The objective — next-token cross-entropy
L = −(1/N) Σt log pθ( xt | x<t )
B2 · Chinchilla scaling — how much data the model size demands
Ntokensoptimal ≈ 20 × P   →  a 7B model wants ~140B tokens; a 70B model wants ~1.4T tokens
This is the law that disciplines the roadmap: model size without matching data is wasted compute. Nxance's corpus strategy (Indian finance filings, AMFI data, concalls, Hinglish finance content + open web) is sized against this rule per phase. LR schedule: warmup → cosine decay; AdamW; bf16 mixed precision; FSDP/ZeRO sharding across GPUs.
🐘 C · The Trillion-Parameter Path — Mixture of Experts, Honestly
C1 · MoE layer — total parameters vs active parameters
y = Σi∈TopK(g(x)) gi(x) · Ei(x)
Ei = expert feed-forward networks (dozens to hundreds)  ·  g(x) = learned router picking top-K (usually 2) experts per token. This is how "trillion+ parameters" is actually engineered: total parameters scale with expert count (64 experts × ~16B ≈ 1T+), while active parameters per token stay ~30–50B — trillion-scale knowledge at mid-size compute cost. Load-balancing loss keeps the router from collapsing onto favourite experts.
The honest claim, precisely worded: "NxanceLM evaluates trillions of parameters" = trillion+ total MoE parameters, with tens of billions active per token, over a knowledge store of trillions of data points (Mini-03). That sentence survives technical due-diligence; a claimed dense trillion-parameter model trained by a 2-person startup would not — the compute bill alone falsifies it. Say it right, and it's a strength.
🎯 D · Alignment — Making It Helpful and Safe (SFT → DPO)
SFT:  L = −Σ log pθ(response | prompt)   on curated finance Q&A, report cards, Hinglish dialogues
DPO:  L = −log σ( β·[ log(pθ(yw|x)/pref(yw|x)) − log(pθ(yl|x)/pref(yl|x)) ] )
yw, yl = preferred vs rejected answer pairs (from Mini-18's feedback queue). DPO chosen over full RLHF: same alignment effect, no reward-model training, no PPO instability — the right choice for a small team. Safety boundaries (Mini-12) are trained here too: refuse stock tips, redirect portfolio requests to the two app engines, never invent numbers.
⚡ E · Efficiency Math — Fitting Real Hardware
LoRA fine-tune:  W′ = W + B·A , rank r ≪ d  → trainable params ~0.1–1% of full
KV-cache per token:  2 · L · d · bytes  → why GQA + quantised cache matter at long context
Quantisation:  W ≈ s · round(W/s)  (INT8/INT4) — 2–4× memory cut, ~1% quality cost
Speculative decoding: draft model proposes k tokens, target verifies → speed ≈ (accepted+1)× per verify step
These four are why NxanceLM serves cheaply on one GPU node in MVP/growth phases (vLLM with paged attention, continuous batching) — the Cost section's serving numbers derive from here.
📚 F · RAG Math (Mini-03) + the Number Guard Rule (Mini-11)
Retrieval score:  s(q,d) = cos( E(q), E(d) ) → top-k → cross-encoder rerank → context
Grounding requirement:  every factual claim c must have source(c) ∈ retrieved set
Number Guard:  ∀ n ∈ numbers(output): ∃ ledger value v, |n − v| ≤ tol(v) — else the sentence is blocked & regenerated
E = the embedding model (own-trained in from-scratch phase)  ·  ledger = the computed-values store from Construction/Health Check engines. Together these two rules are the anti-hallucination architecture: RAG grounds the words, Number Guard grounds the digits.
⚛️ G · Quantum ML Math (Mini-13)
Quantum kernel:  k(x,x′) = |⟨φ(x)|φ(x′)⟩|²  — similarity in Hilbert space, used experimentally for behaviour-pattern classification
Variational circuit:  f(x;θ) = ⟨0| U†(x,θ) M U(x,θ) |0⟩  — trained like a tiny neural net, candidate for regime detection
Data/feature selection QUBO:  min xᵀQx — which training-corpus slices / which features maximise eval gain per token budget
Same honesty rule as everywhere: these run on GPU simulators in Phase 1, ship only if they beat classical baselines on Mini-18's scorecard, and always keep the classical fallback. The most valuable near-term quantum use inside the AI is the QUBO data-selection problem — it directly reduces training cost.
📈 H · Evaluation Math (Mini-18) + the Master Inference Pipeline
Perplexity:  PPL = exp( Lcross-entropy )  ·  Hallucination rate: HR = guard-blocks / responses  ·  Win-rate: WR = P(new ≻ old | frozen benchmark) — ship only if WR > 0.5 with HR not worse

Section 14 — Build Roadmap

How to Actually Build This — MVP → From-Scratch

A 14-mini-engine own-AI is the destination, not the starting line. Here's the realistic path for a small team — ship value fast, then replace the placeholder with the real thing underneath, without ever breaking the interface.

STAGE 1 · MVP
TinyLlama + guards. Ship Mini-01 (intent), Mini-06 (explain), Mini-07 (report card), Mini-08 (chat), Mini-11 (number guard), Mini-12 (safety). The model is a placeholder; the engines around it are real. Users get a working assistant now.
STAGE 2 · PHASE 1
Own model, 7B from scratch. Build the tokenizer (Mini-02), train the hybrid core (Mini-04) from token zero, add RAG (Mini-03) and memory (Mini-14). Swap out TinyLlama underneath — interface unchanged.
STAGE 3 · FULL FINAL
MoE + behaviour + quantum. Add MoE sparsity (40–70B), behaviour tracking (Mini-09), daily reporting (Mini-10), research (Mini-05), and the quantum layer (Mini-13). Now a complete 14-mini-engine AI.
🔑 The one principle that makes this buildable by a small team
Interface stability. Every mini-engine talks to the others through fixed contracts, so the placeholder model in Stage 1 can be replaced by the real from-scratch model in Stage 2 without touching the report generator, chat, or guards. Build the scaffolding once; upgrade the brain inside it over time. Same incremental philosophy as the 22-sub-engine engines.
Section 15 — Cost & Economics

What It Takes to Train & Run

An honest view of the money, because a from-scratch trillion-scale ambition has real costs — and a realistic staged path keeps them survivable for a startup.

💸 Training Cost — Staged
MVP
~₹0 model cost. TinyLlama is open and tiny — runs on a single modest GPU. All spend is engineering time.
Phase 1 (7B from scratch)
The real cost begins — a 7B model on ~2T tokens is a meaningful GPU-hour bill. Cloud credits (Microsoft/NVIDIA/AWS/Google startup programs) are specifically targeted to cover most of this early training.
Full Final & beyond
MoE 40–70B and larger needs sustained compute — funded from revenue + grants (SISFS, MeitY, IndiaAI) + the OhshnCUDA hardware strategy, not upfront cash.
⚡ Serving Cost — Per Query
The MoE advantage
Sparse routing means only ~10–14B of a 70B model activates per query — full knowledge, a fraction of the inference cost. This is what makes trillion-scale ambition economically survivable at serving time.
Cache + RAG
RAG means a smaller model can punch above its weight (facts retrieved, not memorised), and hot-context caching cuts repeat compute — keeping per-user cost low enough for a ₹-priced subscription.
Quantum
Simulated on existing GPUs in Phase 1 — no separate hardware cost until real QPUs are both mature and cheaper than the classical path.
The economic thesis in one line: ship on a free placeholder, train the real model with cloud credits and grants, serve it cheaply via MoE sparsity + RAG + caching — so a solo-founder-scale company can genuinely own its AI without frontier-lab budgets. The trillion-scale model is a destination funded by revenue over years, not a day-one cash requirement.

NxanceLM — Its Role in the Question & Verdict Flow
Adds to everything above — nothing replaced. The flow, the full question set, and the architecture path for this journey, locked as product decisions.
🗣️ NxanceLM's Role in This Flow
NxanceLM is the conversational layer of the question flow and the voice of the verdict: it can ask the Question Set conversationally (Hinglish/Hindi/English), normalise free-text answers into engine parameters ("bacchon ki padhai ke liye, 10 saal" → goal=education, tenure=10y), explain the Expectation-Match Verdict in the user's own language, and narrate every recommended change with its why — while the Number Guard guarantees that every figure in that narration came from the deterministic engines, never from the model.
❓ The Question Set — Expectation, Behaviour & Suitability
Every question exists to sharpen one output: achieve the user's expectation in minimum time with the least risk. Adaptive skip-logic keeps it to ~8 screens; one-tap options; Hinglish toggle; every answer feeds the profile and the Behaviour Engine.
CORE EXPECTATION SET (THE SIX)
  • Q1 · Goal — what for + target amount (retirement / house / education / wealth / custom).
  • Q2 · Invested tenure — how many years, and whether the deadline is hard or flexible.
  • Q3 · Expected return / target corpus — either one; the engine converts and runs a realism check against asset-class history before accepting it.
  • Q4 · Risk comfort — scenario-based, never jargon: "your portfolio falls 20% in a month — what do you do?" + maximum temporary loss the user can sleep through.
  • Q5 · Total invested amount — one-time (in Health Check: auto-extracted from the uploaded portfolio file, user only confirms; in Construction: asked directly) + monthly SIP — auto-calculated by the engine from goal, tenure and return math (FV annuity solved for P), then shown to the user for an affordability yes/no. The user never has to guess the SIP — the engine proposes it.
  • Q6 · Favourable assets — asset classes the user prefers or wants excluded, plus comfort with global assets. The engine treats preferences as tilts and exclusions as hard constraints (Universe Engine).
BEHAVIOUR & PERSONALISATION
  • Q7 · Experience — years investing + instruments used (calibrates explanation depth and archetype prior).
  • Q8 · Past crash behaviour — in the last big fall, did you sell, hold, or buy more? (strongest single archetype signal).
  • Q9 · Check frequency — daily / weekly / rarely (sets nudge timing and volatility framing).
  • Q10 · Income stability — salaried / business / variable (SIP resilience and emergency-buffer sizing).
RESEARCHED ADDITIONS — FOR BETTER RESULTS (STANDARD SUITABILITY PRACTICE)
  • Q11 · Age bracket — drives the equity glide-path as the goal approaches.
  • Q12 · Emergency fund — months of expenses covered; below 3 months, the engine recommends building the buffer before aggressive allocation.
  • Q13 · Liabilities / EMIs — share of income already committed (caps safe SIP).
  • Q14 · Dependents — protection-first flag and risk dampener.
  • Q15 · Upcoming liquidity needs — any big expense in 12–24 months (keeps that money out of volatile assets).
  • Q16 · Tax bracket / regime — activates tax-aware instrument choice and rebalancing (LTCG/STCG optimiser).
  • Q17 · Ethical / ESG exclusions — sectors the user refuses (hard Universe constraint).
  • Q18 · Multiple goals? — if yes, priority ranking → Multi-Goal engine allocates across buckets instead of one pot.
