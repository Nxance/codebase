Section 03 — The Diagnostic Core

Sub-Engine 01 — Analysis Engine, How to Build It Right

This is the single most accuracy-critical engine in Health Check. It decides everything downstream — if it misses a gap, the Guidance Engine never gets to fix it. The core question it answers is not "did the portfolio go up" but "is what I already own actually getting me to MY goal?" — aligned to this user's specific goal, timeline and real risk tolerance.

🔍 The Core Question — "Is What I Own Actually Getting Me There?"
Not just performance
A portfolio can have great returns and still fail the user — wrong timeline fit, too concentrated, wrong risk level for their real tolerance, quietly leaking money to costs. "Is it working" means aligned with THIS user's specific goal, not just "did it go up."
Comparison, not judgement
The engine's fundamental operation is always a comparison: what the user HAS versus what the user NEEDS to hit their stated goal, on their stated timeline, at their stated risk comfort. Every gap is the distance between those two.

How to Build It Well — The 6 Techniques That Make Gap-Finding Accurate

1️⃣ Multi-Dimensional Gap Scoring
Technique
Don't collapse "is this portfolio good" into a single number too early. Score each dimension separately first: Performance gap, Cost gap, Structure/concentration gap, Liquidity gap, Risk-mismatch gap.
Why it matters
A portfolio that's "70% good overall" hides one that's excellent on performance but dangerously concentrated — averaging masks the exact thing that needs fixing. Five separate scores tell the truth a single score buries.
2️⃣ Counterfactual Comparison
Technique
For every held instrument, compute what an equivalent Direct-plan / lower-cost / better-rated alternative would have returned over the same period — the actual rupee difference, not a percentage abstraction.
Why it matters
"You're paying 1.2% more than needed" is abstract and ignorable. "This has cost you ₹34,000 over 3 years" is what makes a user actually act. Rupees move people; percentages don't.
3️⃣ Time-Aware Trajectory Modelling
Technique
Don't just look at where the portfolio is today — project its current trajectory (via Sub-06 Forecasting, Monte Carlo) forward to the goal date and compare against the required trajectory.
Why it matters
A portfolio that's "fine today" can still be on a trajectory that misses the goal by 4 years. That gap is completely invisible without projecting forward — today's snapshot lies about tomorrow.
4️⃣ Root-Cause Attribution THE BIGGEST ACCURACY LEVER
Technique
When a Performance gap is found, decompose WHY: is it fund-selection quality? Cost drag? Asset-allocation mismatch? Or the user's own bad market timing? Different causes need completely different fixes.
Why it matters
Recommending "switch funds" when the real problem is "you panic-sold in 2020 and re-entered late" fixes the wrong thing entirely. This is exactly where Sub-04 Behaviour Analysis feeds back into Sub-01 — separating a bad fund from a bad habit.
Most portfolio tools stop at "your XIRR is low." Nxance's Analysis Engine has to answer WHY, because the Guidance Engine's recommendation is completely different depending on the answer. This single technique is what separates a genuinely useful diagnostic from a generic one.
5️⃣ Materiality Filtering
Technique
Not every gap is worth surfacing. Filter to only the gaps that matter in rupee terms and in impact on the goal — a ₹200 cost leak on a ₹50-lakh portfolio is noise; a 15% over-concentration is not.
Why it matters
Drowning a user in 40 tiny gaps makes them ignore the 3 that actually matter. Materiality filtering is what keeps the report actionable instead of overwhelming — directly serving the "make it easy" part of the motive.
6️⃣ Cross-Validation Against Peers
Technique
Check each detected gap against anonymised outcomes from similar-profile users (same age, goal, timeline, risk) via Sub-13 Peer Comparison — does a "gap" the model flagged actually correlate with worse real-world outcomes for this segment?
Why it matters
Catches cases where the model's theoretical gap doesn't match reality. A "sub-optimal" allocation that peers with identical goals have used successfully for years might not be a real gap at all.

# Analysis Engine — multi-dimensional, root-cause-aware gap finder
class AnalysisEngine:
    """Finds every gap between HELD and NEEDED. Never one score too early."""

    def diagnose(self, held_portfolio, user_goal, user_behaviour):
        gaps = []
        for dim in ["performance", "cost", "structure", "liquidity", "risk_fit"]:
            g = self.score_dimension(dim, held_portfolio, user_goal)  # separate scores
            if self.is_material(g, held_portfolio.value):                # Technique 5
                g.root_cause = self.attribute_cause(g, user_behaviour)  # Technique 4
                g.rupee_impact = self.counterfactual(g, held_portfolio) # Technique 2
                g.confidence  = self.peer_validate(g, user_goal)        # Technique 6
                gaps.append(g)
        # Technique 3: project current trajectory vs required, to the goal date
        gaps += self.trajectory_gaps(held_portfolio, user_goal)
        return prioritise(gaps, by="rupee_impact")  # hand to Guidance (Sub-07)
Why the Analysis Engine is the whole ballgame
Everything downstream — the recommendation, the replacement, the report card — is only as good as this engine's diagnosis. Get the gap wrong and you fix the wrong thing. That's why it uses six independent techniques and feeds off six other engines: a correct diagnosis is worth more than a clever cure.
Section 04 — The Replacement Decision Engine

Sub-Engine 08 — Selection Engine, All 16 Layers

The exact same 16-layer engine as Construction's Selection Engine — but in Health Check it's invoked in a different context: whenever the Guidance Engine decides an existing instrument genuinely needs replacing, not just rebalancing. It scores every candidate replacement across 16 layers, combines them into one FIT score, decides quantity separately, and adds one Health-Check-specific check the Construction version doesn't need: is switching even worth the cost? v1 had 12 layers; v2 adds 4 (Data Analysis, Own AI, Quantum Scoring, Human/Market Behaviour). The iron rule: no single layer decides. The FIT score is the collective verdict of all 16.

🎯 When It's Called — Guidance Engine's Trigger, Not a Standalone Decision
Called when
A held instrument fails Fraud Gate, consistently underperforms its category with no recovery signal, or no longer fits the user's risk profile after a life change. Guidance Engine (Sub-07) decides this — Selection just executes the "find the best replacement" job.
NOT called when
The gap is pure cost (a Direct-plan switch of the same fund — no Selection needed) or pure allocation drift (Rebalancing reweights existing holdings). Selection is only for genuine replacement.

The 16 Layers — Every One, In Detail

How to read this: each candidate instrument passes through all 16 layers in parallel. Each layer returns a 0–100 score. The scores are combined with per-asset-class weights into one FIT score. Layer 8 (Fraud) is special — it's a hard veto, not a weighted score: fail it and the instrument is gone regardless of everything else.
🔬 Layers 1–4 · Instrument Quality
1 · Fundamental Analysis
Stocks/ETFs/REITs: P/E, ROE, debt-to-equity, free cash flow, revenue & earnings growth. FDs/bonds: issuer credit rating (CRISIL/ICRA), coupon vs prevailing market rate, duration risk. MFs: expense ratio, portfolio quality, AUM stability. The "is this fundamentally a good asset?" layer, computed differently per class.
2 · Technical Analysis
Applies where price-action matters — stocks, ETFs, commodities, futures, currency. Moving averages, RSI, volume trends, support/resistance. Deliberately near-zero weight for FDs (an FD has no meaningful chart). Timing and entry-point signal.
3 · Quant Finance
Factor exposure (value, growth, momentum, quality), risk-adjusted return ratios (Sharpe, Sortino, Treynor), beta vs benchmark, and alpha-generation history. This is the academic-grade "how does this behave as a statistical object?" layer.
4 · Instrument-Specific Deep Data
The layer that's different for literally every instrument type: fund-manager track record for MFs, promoter-holding changes for stocks, real yield for gold, occupancy & lease quality for REITs, roll-yield for commodities. Whatever is uniquely decisive for that instrument.
📉 Layers 5–8 · History & Risk
5 · Historical Performance
Full return history — not just the flattering recent stretch. 5-year, 10-year, and since-inception CAGR, each compared against the category average. Catches funds that look great on a 1-year view but chronically lag their peers over a full cycle.
6 · Crisis / Case Analysis
How did this specific instrument behave in 2008, the 2013 taper tantrum, 2018 IL&FS, the 2020 COVID crash, and the 2022 rate-hike cycle? Drawdown depth and recovery time in each. An instrument that fell 70% in 2008 and took 6 years to recover is scored very differently from one that fell 25% and recovered in 8 months.
7 · Risk Analysis (instrument-level)
Standalone volatility (standard deviation), downside deviation, Value-at-Risk, maximum drawdown — the instrument's own risk, before it ever enters portfolio-level risk (that's Sub-09's job). A high-return instrument with brutal standalone risk gets penalised here.
8 · Fraud Analysis — HARD VETO
SEBI/RBI action history, auditor red flags, promoter pledge levels, unusual related-party transactions, governance concerns. This is not a weighted score — it's a gate. Fail it and the instrument is rejected outright, no matter how brilliant every other layer looks. Great fundamentals never buy forgiveness for fraud risk.
🔮 Layers 9–12 · Forward-Looking + Fit
9 · News, Articles & Sentiment
NLP-based sentiment scoring on recent news and analyst coverage. NxanceLM reads and understands article sentiment — it's not keyword counting. A stock with strong fundamentals but a wave of credible negative coverage (regulatory probe, sector headwind) gets flagged before it's picked.
10 · Fresh Performance + Market Mood
The most recent quarter's numbers and the current market mood (a fear/greed-index equivalent). Catches what stale historical data misses — a fund that was excellent for 10 years but just had two bad quarters under a new manager, or a market that's currently euphoric and due for mean-reversion.
11 · Forecasting + Data Science
ML-based forward-return projection, per-instrument — the same Monte Carlo / time-series forecasting family used at the portfolio level, applied to each candidate. This is the "where is this likely to go?" layer, deliberately separated from Layer 13 which interrogates the past.
12 · User Behaviour Fit (volatility)
Does this specific instrument's volatility profile match what THIS user can actually tolerate (from Sub-01's stated behavioural score)? A mathematically optimal but wildly volatile instrument scores low for a nervous user even if it scores high for a calm one. Note: Layer 16 goes deeper on this — Layer 12 is the stated-tolerance check, Layer 16 is the observed-behaviour + crowd-psychology check.

Layers 13–16 — The Four New in v2, In Depth

🗄️ Layer 13 — Data Analysis POWERED BY SUB-19
What it does
A dedicated statistical layer that runs on the full raw dataset of every candidate — not summaries. Distribution analysis (is this fund's return skewed or fat-tailed?), regime detection (does it behave differently in high-inflation vs low-inflation periods?), anomaly detection (any suspicious NAV jumps?), liquidity-depth analysis (can the user actually exit at fair price?), and cross-sectional ranking against every peer in its category.
Why it's separate from Layer 11 (Forecasting)
Layer 11 predicts the future. Layer 13 interrogates the past and present at full statistical depth — it catches data-quality problems and structural oddities that a forecast model would silently absorb as noise.
🤖 Layer 14 — Own AI (NxanceLM) HELPER, NOT DICTATOR
What it does
NxanceLM reads what the other 15 layers cannot read: annual reports, concall transcripts, scheme documents, management commentary, regulatory filings — and cross-checks patterns across the trillions of data points in Sub-19's historical store. It then does two jobs: (1) produces its own 0–100 layer score, and (2) acts as a consistency checker — if Layer 1 says "excellent fundamentals" but Layer 9 sentiment is collapsing, it flags the contradiction and forces a deeper look before the composite is finalised.
How it helps quantity decisions
When deciding how much to hold, NxanceLM contributes context the math can't: "this AMC just lost its star fund manager", "this issuer's audit committee resigned" — soft signals that trim position size even when hard numbers still look fine.
Hard boundary
Its score is exactly one of 16 inputs, weighted like any other layer. It can flag, adjust, explain. It cannot override the collective verdict, and it can never push an instrument past a failed Fraud Gate. This is the "own AI is a parameter, not a dictator" rule made literal.
⚛️ Layer 15 — Quantum Scoring POWERED BY SUB-17
What it does
Classical layers score each candidate independently. Quantum scoring evaluates each candidate in the context of the whole portfolio being built — "how much better does the total portfolio become if this instrument enters it?" That's a combinatorial question (which subset of ~200 shortlisted instruments forms the best portfolio?), and combinatorial subset-selection is exactly the problem class quantum optimisation is designed for.
How, concretely
The shortlist is encoded as a QUBO — every instrument is a binary variable (in/out), expected returns from Layer 11 become the linear terms, pairwise correlations from Sub-05 become the quadratic terms. A QAOA circuit (GPU-simulated in Phase 1) samples low-energy solutions = high-quality subsets. Instruments appearing in many top solutions score high; ones that never appear score low, even if their standalone metrics look great.
Why this matters
This is the layer that catches "great instrument, wrong portfolio" — a top-ranked fund 0.95-correlated with three already-strong candidates scores poorly here, protecting real diversification the standalone layers would miss.
🧠 Layer 16 — Human / Market Behaviour POWERED BY SUB-16
What it does — two sides of behaviour
Market-side: behavioural-finance analysis of the crowd around this instrument — is it currently a herd-momentum favourite (retail inflow spikes, social hype) that history says tends to mean-revert painfully? User-side: deep behavioural match beyond Layer 12 — will THIS user, given their tracked archetype (Sub-16), actually hold this instrument through its normal drawdowns without panic-selling?
Difference from Layer 12
Layer 12 asks "does the volatility number match the user's stated tolerance?" Layer 16 asks "does the crowd psychology around this instrument, plus the user's observed behaviour, make this a hold-able position?" Stated and observed often disagree — Layer 16 trusts observed.

# Composite FIT score — v2, 16 layers, one collective verdict
class SelectionEngineV2:
    """16 layers, weighted per asset class. No layer decides alone."""

    LAYER_WEIGHTS = {
      "stock": {"fundamental":0.14, "technical":0.07, "quant":0.10, "deep_data":0.05,
                "historical":0.06, "crisis":0.06, "risk":0.09, "fraud":0.07,
                "sentiment":0.05, "fresh":0.04, "forecast":0.07, "user_fit":0.05,
                "data_analysis":0.05, "nxancelm":0.04, "quantum":0.04, "behaviour":0.02},
      "fd":    {"fundamental":0.30, "risk":0.18, "fraud":0.14, "crisis":0.08,
                "forecast":0.08, "data_analysis":0.08, "nxancelm":0.06, "user_fit":0.08},
      # ... one weight profile per asset class (gold, REIT, MF, bond, ...)
      # technical ≈ 0 for FDs; crisis + behaviour weigh heavier for gold; etc.
    }

    def score_candidate(self, instrument, asset_class, user, portfolio_ctx):
        w = self.LAYER_WEIGHTS[asset_class]
        s = self.run_all_16_layers(instrument, user, portfolio_ctx)  # parallel
        if s["fraud"] < FRAUD_GATE:      # hard veto — nothing overrides this
            return REJECTED
        s = self.nxancelm_consistency_pass(s)  # flag cross-layer contradictions
        return sum(w[k] * s[k] for k in w)  # 0-100 collective FIT verdict

    def decide_quantity(self, ranked, slot_rs, corr_matrix, user):
        """WHICH = the FIT ranking above. HOW MUCH = this second pass."""
        # top-FIT names get bigger weight in the slot, BUT trimmed down if
        # highly correlated with each other (Sub-05) or if Layer-16 says this
        # user can't hold that much of this volatility profile.
        return weighted_allocation(ranked, slot_rs, corr_matrix,
                                    behaviour = user.archetype)
Two decisions, one engine
Which instrument = the 16-layer FIT ranking. How much quantity = a separate optimisation combining the FIT score, Sub-05 correlations, Layer-15's portfolio-context quantum score, and Layer-16's behavioural hold-ability. A top-ranked stock still gets a smaller slice if three other selected stocks already move the same way, or if this user can't stomach that much of it. Quantities are tuned to hit the user's required XIRR (Sub-01) at minimum risk — not to look mathematically pretty.

🔀 Health-Check-Only Layer — The Switching-Cost Check
What it adds
Before recommending any replacement, Selection asks: is switching worth the cost? Replacing something the user already owns triggers exit loads, potential capital-gains tax, and market-timing risk. A marginally better instrument is NOT worth a taxable event.
# Replacement-specific: only recommend a switch if it clearly pays off
def evaluate_replacement(self, held, user, candidate_pool, reason):
    ranked = [self.score_candidate(c, c.asset_class, user, ctx) for c in candidate_pool]
    best   = max(ranked, key=lambda c: c.fit_score)
    switching_cost   = self.calc_switching_cost(held, exit_load=True, tax=True)
    expected_benefit = self.project_benefit(held, best, user.timeline)
    if expected_benefit <= switching_cost * BREAK_EVEN_MARGIN:
        return None   # not worth replacing — stay put, lowest-risk answer
    return best      # worth it → hand to Guidance → user approves → Execution
This is "minimum risk" as code: the safest fix is often no fix. Selection actively recommends staying put when a switch wouldn't clear its own cost — protecting the user from churn dressed up as advice.

STAGE 1 · MACRO / MAIN PARAMETERS → ASSET-CLASS MIX
Run on the whole portfolio (Health Check) or the whole questionnaire (Construction) to decide the asset-class allocation. Class-agnostic — they see the forest, not the trees:

The Full Health-Check Pipeline — Read → Macro → Select → Engines → Backtest → Report
Every run follows this exact order. The backtest is a hard gate — nothing reaches the user unless the result is verified correct and proven to fulfil the user's expectation.
STEP 1 · READ & UNDERSTAND
Read the uploaded portfolio + the questionnaire
The engine reads what the user holds (every instrument, quantity, buy date, cost) and what they expect — goal, amount, timeline, true risk tolerance from their answers. Nothing is judged yet: this builds the complete has-vs-needs picture.
↓
STEP 2 · MACRO ANALYSIS · STAGE 1
Macro-analyse every held asset vs the user's expectation
Each bought instrument runs through the 15 macro parameters. The question: is this asset even the right kind of asset for this user's stated expectation — right class, right risk, right for the timeline?
↓
STEP 3 · SELECTION · STAGE 2
Find the best alternative — 16 layers, per-asset-class parameters
For every weak/mismatched holding, the Selection Engine runs all 16 layers graded on the parameter pack for that asset's class (above), producing the best alternative and the quantity that moves the user toward the goal.
↓
STEP 4 · ALL OTHER ENGINES
Every other sub-engine adds its part
Risk, Correlation, Forecasting (Monte-Carlo goal probability), Crisis/backtest data, Tax, Behaviour, Peer-Intelligence and Number-Guard each contribute — so the report is complete: exact gap in ₹, goal-probability lift, risk-fit, cost leak.
↓
STEP 5 · BACKTEST · THE GATE
Backtest the report & alternatives before anything reaches the user
The whole report is backtested: is the analysis correct, and would the alternatives have fulfilled the user's expectation across real history + the 5-crash stress set? PASS → report. FAIL → loop to Step 3. Nothing that fails is ever shown.
↓
STEP 6 · REPORT TO USER
Deliver the plain-language report
Only on PASS: the report states what is wrong, the main reason it exists, the best alternative, the quantity, and exactly why this one was chosen — in language a retail investor understands.
The Backend Number System — Everything Becomes a Score
To keep all of this fast and objective, the engine turns every single thing into a number behind the scenes. Every parameter, every layer, every instrument gets a score; the engine simply picks the highest-scoring options when analysing the portfolio. This is 100% backend — the user never sees raw numbers, only the plain-language result and its reason.
HOW SCORING WORKS (HIDDEN)
1 · Each macro parameter scores every asset 0–100 (Stage 1).
2 · Each per-asset-class parameter scores every instrument 0–100 within its own category (Stage 2, z-scored).
3 · Layers combine into one FIT score per instrument (weighted per class).
4 · The Fraud gate can zero out any score (hard veto).
5 · The engine ranks by score, picks the best; quantity is a second scored pass (correlation + behaviour trim).
6 · The whole result gets a backtest score — the pass/fail gate before the user sees anything.
USER SEES vs BACKEND DOES
Backend (hidden): hundreds of 0–100 parameter scores, FIT scores, correlation matrices, rank tables, backtest scores — pure math in the Rust/Python core.
Front-end (shown): only the outcome in plain language — "this holding drags you down because X; the better fit is Y; here's how much; here's why." No raw scores, no formulas on screen.

Choose=argmax(FIT) per slot · Quantity=f(FIT, correlation, behaviour)
Backtest=PASS if accuracy≥θ AND expectation-fulfilled≥θ, else loop
The rule (Number Guard): the Rust/Python core computes every score; NxanceLM can explain any number in words but computes none. Scores drive the decision; language delivers it; the raw number system stays hidden from the user.

Diagnose Layer — Engines That Feed the Analysis Engine

⚠️ SUB-02 · Risk Analysis Engine DIAGNOSE · EVERY CHECK-IN
What it measures
The current portfolio's VaR, CVaR, maximum-drawdown exposure, and downside deviation — the exact same risk metrics as Construction's Risk Engine, applied to what's already held.
The key question
Is the current risk level higher than it needs to be to still hit the goal? If a user is taking equity-heavy risk when their timeline no longer requires it, that's a specific, fixable gap — often the safest win in the whole report.
Feeds
Directly into Analysis Engine's Risk-mismatch dimension, and sets the risk boundary any Guidance recommendation must respect.
🛡️ SUB-03 · Fraud Gate DIAGNOSE · HARD VETO
7 hard checks
SEBI/RBI action history, auditor red flags, promoter pledge levels, related-party transactions, unusual volume spikes, delisting risk, and category mismatch — run on every instrument the user already holds.
Hard veto
Any held instrument that fails is flagged for immediate replacement regardless of how the rest of the analysis scores. Great past returns never buy forgiveness for fraud risk — this flag never gets averaged away.
Why it matters in Health Check
Users often hold a fraud-flagged name for years without knowing. Catching it is one of the highest-value things a Health Check can do — it's pure downside protection.
🧠 SUB-04 · Behaviour Analysis Engine DIAGNOSE · EVERY CHECK-IN
What it detects
FOMO buying, herd-following, panic-selling during drawdowns, recency bias — read from the user's own transaction-timing history in their existing portfolio. This is behaviour evidence, not a questionnaire guess.
Feeds back into root-cause
Directly into Sub-01's root-cause attribution (Technique 4) — this is the engine that separates "bad fund choice" from "bad timing behaviour." If a user's underperformance is caused by panic-selling, no fund switch fixes it — the fix is behavioural.
Works with Sub-16
Sub-04 analyses past behaviour in the existing portfolio; Sub-16 (the new Supervision engine) maintains the live, evolving behaviour archetype. Together they give both history and trajectory.
💰 SUB-05 · Tax Efficiency Engine DIAGNOSE · EVERY CHECK-IN
What it tracks
FIFO lot-level LTCG/STCG status per holding, unused tax-harvest opportunities, and 80C utilisation — the tax reality of the existing portfolio at the individual-lot level.
How it constrains fixes
Any change the Guidance Engine recommends must pass through Sub-05 before being finalised — it never triggers unnecessary short-term capital gains just to close a gap. A fix that creates a bigger tax bill than the gap it solves is not a fix.
Also surfaces
Tax-harvest wins the user didn't know they had — booking a loss to offset gains — a pure-upside recommendation with near-zero risk.
🔮 SUB-06 · Forecasting Engine DIAGNOSE · EVERY CHECK-IN
Method
Monte Carlo simulation — 10,000 paths, CUDA-accelerated — projecting the current portfolio's trajectory forward to the goal date. Not a single-point guess but a full distribution of likely outcomes.
What it powers
Analysis Engine's Technique 3 (Time-Aware Trajectory Modelling) directly. This is the engine that reveals a portfolio which looks fine today but is on track to miss the goal by years.
Output the user sees
"On current trajectory: ~78% probability of reaching your goal on time" — and if that number is low, it becomes the headline gap the whole report is built around.
👥 SUB-13 · Peer Comparison Engine DIAGNOSE · EVERY CHECK-IN
Method
Anonymised cohort benchmarking — compares the user against similar-age, similar-goal, similar-timeline, similar-risk users who Nxance has real outcome data on.
What it powers
Analysis Engine's Technique 6 (Cross-Validation Against Peers). It's the reality check that stops the engine flagging a "gap" that peers with identical goals have used successfully for years.
Privacy
Strictly aggregated and anonymised — the user sees "people like you" patterns, never any individual's data.

Advise Layer — Turning Gaps Into the Safest Fix

💡 SUB-07 · Guidance Engine ADVISE · THE ADVISORY CORE
Its one job
Give the best advice on the current portfolio to achieve the user's result with minimum risk. It takes the materiality-filtered, root-cause-attached gaps from Analysis and decides the safest way to close each one.
The Decision Logic — Fix in Place vs Replace
Behaviour-caused gap
No trade at all. The recommendation is education / a nudge, delivered conversationally by NxanceLM. You can't fix a timing habit by switching funds.
Cost-caused gap
Simplest fix. A Regular-to-Direct switch of the SAME fund — no Selection Engine needed, near-zero risk, pure cost saving.
Quality/Fraud-caused gap
Genuine replacement. Hands off to Sub-08 Selection to find the best alternative — with its switching-cost check.
Allocation-caused gap
Structural rebalance. Hands off to Sub-11 Rebalancing to reweight existing holdings.
"Minimum risk" as the actual optimisation target: when multiple valid fixes exist for the same gap, Guidance always ranks the lowest-risk-to-execute option first. A Direct-plan switch (near-zero risk) always outranks a full fund replacement (timing risk + potential tax event) if both close the same gap. The safest fix wins, not the flashiest.
🕒 SUB-09 · Backtesting Engine ADVISE · BEFORE RECOMMENDATION SHOWN
What it proves
That the recommended change — not just the current portfolio — would have survived the five real crashes: 2008, 2013 taper, 2018 IL&FS, 2020 COVID, 2022 rate-hikes. It replays the post-fix portfolio through each.
Why it runs before the user sees the fix
A recommendation that looks great in calm markets but would have collapsed in 2008 is a bad recommendation. Backtesting is the gate that catches it before it's ever shown — the fix has to prove itself against history first.
v2 addition — behavioural backtest
Also checks "would THIS user have held the recommended fix through its worst drawdown?" — using the Sub-04/Sub-16 behaviour profile. A fix the user would panic-sell isn't a fix.
Section 05 (cont.) — The Manage Layer

Engines 10–15 — Keeping the Fix On-Track for Years

Once the user executes a recommended fix, these engines take over and run for the life of the portfolio. The rule that governs all of them: they observe and propose, they never trade silently — every real-money action is explained and needs user approval. After every executed change, a fresh Health Check runs.

👀 SUB-10 · Analysis & Managing Engine MANAGE · DAILY
Kicks in when
The user actually executes a recommended change. From that moment it becomes the daily heartbeat of the now-managed portfolio.
What it checks daily
Whether the executed fix is performing as projected, weight drift vs the new target, and any instrument whose score suddenly drops (a new fraud flag, a downgrade). It watches everything, decides nothing alone.
Hands off to
Sub-11 (Rebalance), Sub-12 (Redesign), or Sub-14 (Goal-Drift) when a threshold is crossed. Feeds its daily digest to Sub-18 for the report cards.
⚖️ SUB-11 · Rebalancing Engine MANAGE · EVENT-DRIVEN
Triggers on
An asset-class weight drifting beyond threshold (typically 5%), or an instrument-level Fraud Gate failure appearing after execution. Same engine as Construction's rebalancer.
What it does
Computes the exact sell/buy amounts to restore target allocation, tax-checked via Sub-05 (never needless STCG), and proposes it — explained plainly by NxanceLM — which the user approves before Sub-15 executes.
v2 change — behaviour-adapted
The rebalance framing adapts to the archetype: calm, context-first for a Panic-Prone user; raw numbers and tighter thresholds for a Disciplined one. Same math, delivery tuned to keep the user invested.
🔄 SUB-12 · Redesigning Engine (SIP) MANAGE · MONTHLY + ON-DEMAND
Monthly trigger
Runs every SIP cycle automatically — checks if anything's changed enough to adjust this month's contribution. Usually just executes the plan at current prices.
Amount-change trigger
Increase: recomputes allocation, may unlock higher-minimum instruments (via Sub-22). Decrease: recomputes required XIRR/timeline and tells the user honestly if the goal now needs revising. Identical logic to Construction's redesigner.
🎯 SUB-14 · Goal-Drift Watchdog MANAGE · EVENT-DRIVEN
What it does
Watches for signals the user's original goal itself no longer matches reality — new dependents, a changed target amount mentioned in chat, changed timeline urgency, an income shock.
The gap it closes
Rebalancing fixes drift within an unchanged goal. Redesigning fixes SIP amount within an unchanged goal. Neither catches "the goal itself is now wrong." This triggers a full fresh Health Check from Sub-01 with the new inputs — the only engine that restarts the whole diagnosis.
Always confirmed
Inferred signals are always confirmed with the user before a re-analysis — never assumed.
✅ SUB-15 · Execution & Order Engine MANAGE · EVERY ACTION
What it does
The only engine that touches real money. Converts every approved recommendation — a switch, a rebalance, a redesign — into actual orders, SIP mandates, and payment triggers. (New in v2 as an explicit engine; in v1 this was implied inside the manage engines.)
Talks to
Payments service (Go) for mandates, Razorpay for money movement, BSE StAR MF / exchange / broker APIs for orders, and the Notification service to confirm every executed action.
The hard rule — user approval, always
Nothing fires without explicit approval for the specific action. Built as an idempotent state machine with a full audit log — essential for reliability and SEBI compliance. "Easy" never means "automatic without consent."
The Manage layer in one line
Sub-10 watches, Sub-11 fixes drift, Sub-12 handles the SIP, Sub-14 catches goal changes — and Sub-15 is the single hand that touches money, only ever after you say yes. Together they make sure a fix that was right on the day you approved it stays right for years.
Section 06 — New Supervision Engine

SUB-16 · User Behaviour Engine

The insight this engine is built on: multiple users can have the same goal, same risk capacity, same timeline — and still need different analysis and different advice, because no two people behave the same way when markets move. In Health Check, Sub-16 shapes how the existing portfolio is analysed, what fixes are recommended, and — if the user executes — how it's tracked, managed, rebalanced and redesigned, all in the style that keeps THIS user invested until the goal is reached.

🧠 Why the Same Portfolio Gets a Different Verdict per User
Two users hold the identical under-performing fund. For a Disciplined user, the right advice might be "switch to a better fund and hold through volatility." For a Panic-Prone user, the same switch into a higher-volatility (but mathematically better) fund is wrong advice — they'll sell it at the first dip and lock in a loss. Sub-16 is why Health Check gives advice the user will actually follow through on, not just advice that's optimal on paper.
🔍 How It Learns the User's Behaviour
From the existing portfolio (observed — the truth)
This is Health Check's advantage: the user already has a transaction history. Sub-16 reads it directly — did they panic-sell in past dips? Chase last year's winner? Never book profit? Pause SIPs in bad months? This is real evidence, not a guess (shared with Sub-04).
Ongoing (live signals)
App-open frequency, what they check first, how they react to red days, whether they act on recommendations fast/slow/never. The archetype updates continuously — a user can migrate from Panic-Prone to Disciplined over time, and their advice style migrates with them.
Stated vs observed: people say "high risk tolerance" and panic at −8%. Because Health Check can see the user's actual past behaviour, Sub-16 here is even stronger than in Construction — it always weights observed over stated, and it already has the evidence on day one.

If the user executes a recommended fix, Sub-16 stays attached for life: it tracks (behaviour + portfolio health together), manages (tunes Sub-10's alert style per archetype), rebalances (Sub-11's thresholds and framing adapt), and redesigns (Sub-12 SIP changes proposed the way this user is most likely to accept). Section 07 — New Supervision Engine

SUB-17 · Quantum Supervisor Engine (Q-Core)

A dedicated quantum sub-engine whose job is to monitor the entire Health Check engine — every stage, every intermediate output — and verify that the final recommendation gets the user to their goal with minimum risk, in the minimum time period, while making the whole process easier. It doesn't diagnose or pick instruments itself; it supervises the search for the single best fix.

⚛️ Job 1 — Global Optimality of the Fix
The Advise pipeline makes decisions stage by stage (which gap → which fix → which replacement). Stage-wise decisions can be locally right but globally sub-optimal. Q-Core re-encodes the entire post-fix portfolio as one big QUBO — instruments, quantities, correlations, risk constraints, required XIRR, and behaviour constraints together — and searches the full combinatorial space for any configuration that reaches the same goal with less risk or less time. If it finds a meaningfully better one, the pipeline re-runs with its hint; if not, the recommendation is certified.
🎲 Job 2 — Quantum Monte Carlo Risk Verification
Independently re-verifies Sub-02's risk numbers using quantum-amplitude-estimation-style Monte Carlo (simulated in Phase 1). Classical Monte Carlo needs ~1M paths for tight VaR confidence; amplitude estimation reaches the same confidence quadratically faster — which is what makes a full independent risk re-check affordable inside the 10-second budget. If Q-Core's VaR disagrees with Sub-02's beyond tolerance, the recommendation is not released until resolved.
⏱️ Job 3 — Minimum-Time Path Search
Users don't just want to reach the goal — they want it as early as safely possible. Q-Core runs the corrected portfolio as a multi-period optimisation: across thousands of SIP-step / glide-path combinations, which reaches the target earliest without ever breaching the risk boundary? Multi-period path problems explode combinatorially — exactly the shape quantum sampling handles well.
🧭 Job 4 — Process Simplification Monitor
Watches the pipeline itself: which stages take longest, which re-run loops fire most, where users drop off. Produces optimisation hints for Sub-20 (speed) and product hints for the team. Supervision includes making the machine simpler, not just the recommendation better.
⚖️ Q-Core also obeys the Golden Rule
Q-Core verifies and proposes — it never overrides. Its "better fix found" output goes back through the same collective pipeline (Guidance → Selection → Backtest) before anything changes. A quantum result that can't survive the classical checks is discarded. And every Q-Core computation runs with a classical fallback — if the quantum path times out, MVO + classical Monte Carlo results stand, and the Health Check still completes in budget. 🔒 SUB-24 · Number Guard Engine RUST VERIFIER · THE MOST CRITICAL PIECE
The problem it kills
LLMs hallucinate numbers. One invented XIRR in a health report, one wrong drawdown figure, and Nxance's credibility — and SEBI standing — is gone. So the platform enforces one iron rule: NxanceLM never outputs a number the deterministic engines didn't compute.
How it works
A Rust digit-verifier sits between NxanceLM and the user. Every numeric token in every generated sentence (health reports, gap explanations, suggestions, report cards) is parsed and matched against the computed-values ledger for that analysis — the exact outputs of Sub-01…23, each with a provenance ID. A number with no matching ledger entry (within rounding tolerance) → the sentence is blocked and regenerated with the correct injected value. Zero exceptions, zero LLM discretion.
Verification rule
∀ n ∈ numbers(LLM output): ∃ ledger entry v with |n − v| ≤ tol(v) — else BLOCK. Runs in microseconds per message; also stamps every user-visible number with its source engine — exactly what Sub-26 needs for audit.
👥 SUB-25 · Peer Intelligence Engine REALITY-CHECKS THE MODEL

Section 11B — The Quant Core

Formulas, Algorithms & Math — Engine by Engine

Every number in every health report comes from a formula on this page. This is the exact math each sub-engine runs — the same reference Raghav codes against and the same math an investor's technical due-diligence will test. Every formula runs in the Rust calc core or the Python quant layer — NxanceLM can explain any of them, but computes none of them (the Number Guard rule, Sub-24).

📋 A · Portfolio XIRR & Goal Math (Analysis Engine + Profile)
A1 · Actual XIRR of the uploaded portfolio — from real cashflows
Solve for r:  Σk CFk / (1+r)tk + Vtoday/(1+r)tnow = 0
CFk = every actual buy (negative) and sell/dividend (positive) parsed from the uploaded portfolio, at its real date tk (in years)  ·  Vtoday = current market value. Solved by Newton-Raphson with bisection fallback (Newton can diverge on irregular cashflows — the fallback guarantees an answer). This is the honest "what did you actually earn" number — computed per instrument, per asset class, and for the whole portfolio.
A2 · Required XIRR going forward — the gap that matters
Solve for r:  Vtoday(1+r)T + P·[((1+i)12T − 1)/i]·(1+i) = Goal  ,  i = (1+r)1/12 − 1   →   Gap = rrequired − rexpected(current mix)
Bisection, 60 iterations, microseconds in Rust. Gap > 0 = the current portfolio cannot reach the goal → the report says so plainly, with the exact shortfall in ₹ and the safest fixes. If rrequired exceeds the user's safe ceiling, the engine proposes new timeline/target — never silent extra risk.
🩺 B · The Health Score — One Number, Honestly Computed
B1 · Composite (0–100)
HS = Σc wc · sc  ,  components c ∈ {returns vs goal, diversification, cost efficiency, risk fit, quality, tax efficiency, behaviour fit}
Each component score sc is 0–100 (normalised per B2); weights wc sum to 1 and are published inside the report — no black box. Typical profile: returns-vs-goal 0.22, diversification 0.18, risk fit 0.16, quality 0.16, cost 0.12, tax 0.08, behaviour fit 0.08.
B2 · Hard caps — the score cannot lie
HS ← min(HS, 40) if any holding fails the Fraud Gate  ·  HS ← min(HS, 55) if portfolio risk exceeds the user's tolerance band  ·  HS ← min(HS, 60) if P(goal) < 40%
A portfolio with a fraud-flagged holding can never look "healthy" no matter how good everything else averages out — caps are constraints, not weighted terms. Same philosophy as Selection's fraud veto.
🔬 C · Diagnostic Math — Overlap, Concentration, Cost Leak, Drift
C1 · Fund overlap (the hidden non-diversification detector)
Overlap(A,B) = Σh min( wh,A , wh,B )  × 100%
Summed over every underlying holding h of funds A and B (from AMFI/scheme disclosures in Sub-19). Two funds at 78% overlap = one bet bought twice — a classic Indian retail mistake the report flags with the exact percentage and the shared top holdings.
C2 · Concentration — Herfindahl-Hirschman Index
HHI = Σi wi²  ·  effective number of independent bets:  Neff = 1 / HHI
Computed at instrument, sector and asset-class level. A 12-fund portfolio with Neff = 3.1 is really three bets wearing twelve costumes — the report says exactly that, with the numbers.
C3 · Cost leak — the rupee counterfactual
Leak = Σt Vt · (ERheld − ERalt)   compounded over the actual holding period, reported in ₹
ER = expense ratio; alt = the direct-plan / lower-cost equivalent of the same or better-rated fund. "This regular plan cost you ₹47,300 more than its direct plan over 4 years" — a rupee number, not a percentage abstraction.
C4 · Allocation drift vs the user's correct target
driftc = | wcurrent,c − wtarget,c(RS′, T) |  → flagged when driftc > θ (≈5%)
📊 D · Performance & Quality Ratios (per holding + portfolio)
Sharpe: (Rp − Rf)/σp  ·  Sortino: (Rp − Rf)/σdown  ·  σdown = √E[min(R−MAR,0)²]
Beta: β = Cov(Ri,Rm)/Var(Rm)  ·  Alpha: α = Ri − [Rf + β(Rm − Rf)]  ·  IR: (Rp − Rbench)/TE
Rolling consistency:  C = P( 3yr rolling return ≥ category median ) across all windows
Every held instrument is z-scored against its own category (z=(x−μ)/σ → s=100·Φ(z)) so a small-cap fund is judged against small-cap funds — cross-category comparison without normalisation is how naive report cards go wrong.
⚠️ E · Risk Mathematics (Sub-09 equivalent)
Parametric VaR: VaRα = −(μp − zασp)·V  ·  Historical VaR: −quantile1−α(P&L) — report the worse of the two
CVaR: E[L | L ≥ VaRα]  ·  Max Drawdown: maxt((Peakt − Vt)/Peakt)
Portfolio variance: σp² = wᵀΣw  — Σ from crisis-window correlations, Ledoit-Wolf shrunk
Risk-fit check: the portfolio's CVaR and historical MDD are compared against the tolerance band implied by the user's behaviour-adjusted risk score RS′. Outside the band → the Health Score cap (B2) fires and the report explains which holdings drive the excess.
🔮 F · Forward Projection — Goal Probability
GBM paths:  St = S₀·exp((μ − σ²/2)t + σWt)  (Student-t innovations, df≈5, for fat tails)
P(goal) = (1/N)·Σk 𝟙[FVk ≥ Goal]  , N = 10,000 paths of current mix + planned SIP
Computed twice: once for the current portfolio and once for the post-fix portfolio (Sub-23 sandbox) — the "62% → 88%" pair is the single most persuasive number in the report. Q-Core re-verifies via amplitude-estimation Monte Carlo (H4).
🎯 G · Replacement Decision — FIT Score + Switching-Cost Rule (Sub-08)
G1 · Composite FIT (16 layers, per asset class weights)
FIT = Σℓ=1..16 wℓ,class · sℓ  subject to  sfraud ≥ gate (else REJECTED)
G2 · The switching-cost inequality — no churn for churn's sake
Replace holding H with candidate C only if:  E[ΔReturn]·V·Tremaining  >  ExitLoad(H) + Tax(H) + TxnCost + margin
Tax(H) = realised STCG/LTCG from selling now (versioned Indian tax rule table)  ·  margin = safety buffer (default 1.5×) so borderline switches don't happen. A slightly better fund that costs more in exit load + tax than it will ever earn back is not suggested — this inequality is why users can trust the suggestions aren't churning them.
G3 · Quantity of the replacement
qi ∝ FITi × (1 − ρ̄i) × Hi → normalised, capped per class
ρ̄i = mean correlation with what the user keeps  ·  Hi = behavioural hold-ability from Layer 16 (J2 below).

🔧 How It's Built — the Hybrid Loop, Step by Step
  • Step 1 — Formulate as QUBO. Every quantum use-case above reduces to: minimise x'Qx where x is a binary vector (instrument in/out, trade yes/no, path chosen/not). Expected returns fill the diagonal of Q; correlations and penalty terms (risk boundary, budget, cardinality) fill the off-diagonal. This formulation step is 80% of the real engineering work — and it's pure classical Python.
  • Step 2 — Sample with QAOA. The QUBO maps to an Ising Hamiltonian; a parameterised QAOA circuit (typically p=2–4 layers) is run many times; a classical optimiser (COBYLA/SPSA) tunes the circuit parameters between runs. Output: a distribution of candidate solutions, best ones kept.
  • Step 3 — Classical post-check. Every quantum-proposed solution is re-evaluated exactly, classically (Sharpe, VaR, constraints). Only solutions that beat the classical baseline on real numbers survive. Quantum proposes, classical verifies — always.
  • Step 4 — Fallback guaranteed. Timeout, noisy result, or service failure → MVO + classical Monte Carlo answer ships. The user never waits on quantum, and never receives a quantum-only, unverified result.
Phase 1 · Now (MVP → v1.0)
GPU-simulated quantum. All circuits run on simulators (Qiskit Aer / cuQuantum on a single GPU box). Up to ~30–35 qubits simulable — enough for real QUBO problems after classical pre-reduction (shortlist per asset class, then quantum across the shortlist). Zero QPU cost, full control, deterministic testing.
Phase 2 · Growth
Cloud QPU, selectively. AWS Braket / IBM Quantum / D-Wave Leap for the largest problem instances (multi-goal, full-universe Q-Core sweeps), pay-per-task. Simulator remains the default; QPU is reserved for problems that exceed simulator size.
Phase 3 · Full Final
Dedicated quantum capacity. Reserved QPU access or on-prem annealer once scale justifies it. Q-Core runs continuous background sweeps across all live portfolios overnight, surfacing "a better configuration now exists" alerts.
🟡 Honest reality check — read this before telling investors "quantum-powered"
In 2026, for problem sizes Nxance actually faces, GPU-simulated quantum and good classical solvers usually tie or classical wins. The genuine advantages of building the quantum layer now: (1) the QUBO formulation itself often produces better portfolios than naive MVO because it handles messy real-world constraints natively, (2) the architecture becomes hardware-ready — when QPUs mature, Nxance flips a backend flag while competitors start from zero, (3) it is a real, defensible differentiator in the Indian wealthtech market. The honest pitch line: "quantum-inspired optimisation today, hardware-quantum ready by design" — that phrasing survives technical due-diligence; "we use quantum computers" does not. Best advice: build Q1 + Q2 first (they share the QUBO core), prove they beat MVO on backtests, and only then expand to Q3–Q5.
