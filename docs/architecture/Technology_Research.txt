0. Key Clarification — What Nxance Builds vs. What It Buys
This document sets the technology plan straight on one point that changes the entire scope: Nxance does not build, train, or fine-tune its own language model — not even a self-hosted open-source fine-tune. NxanceLM's chat layer runs entirely on a third-party LLM, accessed via API.
What Nxance does build, train, and own outright:
	•	Health Check Engine — 26 sub-engines, deterministic quant math, calibrated in-house
	•	Construction Engine — 26 sub-engines, deterministic quant math, calibrated in-house
	•	Terminal — the market data / news dashboard, zero AI, entirely Nxance's own data pipeline and UI
"Trained" for the two engines means something different from AI training: it means their scoring weights (the Selection Engine's 16-layer FIT score, the Health Score) are calibrated — hand-set by domain judgment, then backtested against historical data — not learned by a neural network. This is the honest, accurate way to describe the engines' "training" without overstating it as machine learning.
This single decision removes GPU training clusters, fine-tuning pipelines, and ML-training hires from the entire plan below — those are the biggest cost and complexity items a technology plan like this usually carries, and none of them apply here.

5. How to Build — Flow

Sequenced so Health Check and Construction are demoable before any AI integration begins.
	•	Step 1 — Auth + Users + Plans: no engine dependency, pure foundation.
	•	Step 2 — Number Guard + Retrieval (RAG) pair: build these before the rest of the AI layer, since every AI-touching feature depends on them existing and passing tests.
	•	Step 3 — Health Check + Construction engines: wire the 26+26 sub-engines behind API endpoints. This is where nearly all of the quant work lives, and it needs zero AI to function or demo.
	•	Step 4 — Dashboard: depends on Step 3 for portfolio valuation.
	•	Step 5 — Reports: depends on Step 3, adds Monte Carlo distribution output and portfolio beta/overlap views.
	•	Step 6 — Billing/paywall gating: one shared has_feature(user, flag) helper, applied consistently rather than scattered per endpoint.
	•	Step 7 — Terminal: independent, can be built in parallel with Steps 1–6, zero AI.
	•	Step 8 — NxanceLM chat integration: deliberately last — this is a thin integration layer (third-party API + RAG + Number Guard wrapper), not a build project of its own, and it depends on the engines above already producing trustworthy numbers to narrate.
This order means Health Check and Construction — the actual quant product — can be built, tested, and demoed end-to-end before a single line of AI-integration code is written.

Since NxanceLM is a third-party model accessed via API, the choice is commercial, not technical — which vendor's API is called, not what gets trained.

9. Equipment & Infrastructure Needs
Because there is no in-house model training, the equipment list is short and inexpensive relative to a typical AI-startup plan:
	•	Developer workstations/laptops — standard development machines for the team, no special GPU requirement
	•	Cloud hosting — Railway to start (matches the decided stack), scales with usage rather than requiring upfront hardware purchase
	•	Database hosting — Supabase-managed Postgres to start
	•	Market data vendor subscription — a licensed NSE/BSE/MCX data feed (e.g. an authorized vendor such as Global Datafeeds) — a recurring cost, not equipment, but budgeted alongside infrastructure
	•	News feed subscription — a budgeted news API rather than ad-hoc scraping
	•	Standard dev tooling — GitHub/GitLab, CI/CD (GitHub Actions), error monitoring (e.g. Sentry)
No GPU training cluster, no dedicated ML hardware, and no data-center commitment are needed anywhere in this plan — that entire category of cost is removed by using a third-party LLM.

11. Performance Architecture
Target: under 10 seconds for an interactive Health Check or Construction result.
	•	A nightly batch job (Data Intelligence Engine) pre-scores the full instrument universe once — not recomputed per request.
	•	At request time, engines read from this pre-scored universe (Postgres, hot data cached in Redis).
	•	Independent sub-engines (Risk, Correlation, Tax, Behaviour) run concurrently, not sequentially, inside a parallel engine DAG.
	•	Rust hot paths handle Number Guard and any other latency-critical calculation.
The expensive computation happens off the user's request path entirely — this is what makes the sub-10-second target realistic without special hardware.
12. Security & Compliance-Relevant Technology
	•	Encryption at rest for PAN, holdings, and financial goal data — never logged in plaintext, including error logs
	•	TLS everywhere, including internal service-to-service calls as infrastructure grows
	•	A versioned audit trail — every computed number traces to an engine_id, a version, and an input-data snapshot
	•	Regulatory mode gating (Analytics / Research / Personalized Intelligence / Execution) enforced at the API layer, not left as policy alone
	•	Consent-scoped behavioral tracking — its own toggle, separate from account-creation consent
	•	A defined retention policy on uploaded CAS/broker files that may contain PAN or date-of-birth data
13. Key Takeaways
	•	Dropping in-house LLM training removes the single most expensive and highest-risk line item from the technology plan — GPUs, ML-training hires, and a training pipeline all disappear.
	•	What remains to build — Health Check, Construction, Terminal — is 90%+ deterministic math with 70+ years of published research behind it, not novel AI research.
	•	The AI Integration Engineer role (third-party API + RAG + Number Guard) is materially cheaper and faster to hire for than an ML/fine-tuning specialist would have been.
	•	Every user-visible number still traces to an engine_id + version + input snapshot — the trust story doesn't weaken just because the model itself is bought, not built.
