1  Executive Technical Summary
Nxance is specified as a diagnosis-first investment-intelligence platform built around three user-facing systems: Health Check, Construction, and NxanceLM. Health Check diagnoses an existing portfolio; Construction builds a goal-aware portfolio; NxanceLM supports the research, analysis and plain-language explanation behind each diagnosis and portfolio build, in addition to conversational intake, retrieval, reporting and supervised cross-engine assistance. The technical blueprints go beyond the simplified pitch description by defining 26+ sub-engines in each investment engine and 18+ coordinated mini-engines in NxanceLM. [S2-S5]
Core architecture thesis
Financial truth is computed by deterministic or independently testable quant/data engines. NxanceLM may retrieve, interpret, cross-check and explain those results, but it does not become the sole source of portfolio numbers or the lone investment decision-maker.

1.1 Product-level architecture

Figure 1. Shared intelligence services underlying Health Check, Construction and NxanceLM.
The source designs make clear that Health Check and Construction should not be implemented as completely separate stacks. They share the Selection Engine, Risk Engine and a broader set of foundation/supervision services: Data Intelligence, Behaviour, Q-Core, NxanceLM, Speed/Orchestration, Number Guard, Peer Intelligence and Compliance/Audit. [S3-S4]
1.2 Non-negotiable design invariants
•  Collective Decision Principle. No single engine, parameter, AI model or quantum component independently determines a user-facing portfolio verdict.
•  Deterministic numbers. Every portfolio number shown by NxanceLM must be sourced from the computed-values ledger or a retrieved, attributable external fact.
•  Hard gates stay hard. Fraud, suitability, regulatory-mode and user-approval controls are constraints, not scores that can be averaged away.
•  Classical baseline always exists. Quantum or advanced-model paths may improve a result only after an exact/classical comparison; failure or timeout falls back safely.
•  Auditability. Every recommendation should be reconstructable from input snapshot, engine versions, scores, constraints, evidence and approvals.
•  Staged regulation. Analytics/education can precede regulated personalised advice or execution; real-money actions remain gated until the relevant approval/partner model is active.
1.3 Current versus target architecture

Figure 2. Current pitch-level implementation versus staged target architecture.
Pitch materials describe a lean current stack of FastAPI + Supabase + Railway and an 80%-code-complete product claim. The deep engineering blueprints describe a target service architecture using Python, Rust, Go, TypeScript, gRPC/protobuf, event streaming, Redis, PostgreSQL/TimescaleDB, vector retrieval, observability and eventually Kubernetes. [S2-S5] The correct interpretation is architecture evolution: keep the current MVP deployable while progressively extracting latency-, correctness- and scale-critical services behind stable contracts.

3.4 NxanceLM interaction boundary
NxanceLM can conduct the intake conversationally, normalize free text into structured parameters, explain verdicts, answer general finance/economy questions, and narrate engine outputs. A request to build or diagnose a portfolio should route into Construction or Health Check rather than being answered as a free-form chat recommendation. [S5]
Product boundary
Chat can explain and research; the portfolio engines compute and decide collectively. This distinction is a product safety mechanism, not merely a UX choice.

7  Health Check Engine Specification

7.3 Health Score and Expectation-Match Verdict
The source design defines a 0-100 Health Score combining returns-vs-goal, diversification, cost efficiency, risk fit, quality, tax efficiency and behaviour fit. It also defines hard caps for specific states (fraud, excessive risk, low goal probability). These weights/caps are design parameters and must be calibrated/approved through governance before public claims. [S3]
HS = sum_c (w_c * score_c)  Hard-cap concept (source design): - fraud-gate failure -> cap score - risk outside user band -> cap score - very low P(goal) -> cap score  Expectation-Match Verdict = deterministic comparison of current/proposed P(expectation achieved), risk and gap impact.

7.4 Advise: fix in place before replacement
•  Guidance Engine. For each material gap, decide whether the safest fix is education/no trade, in-place change, rebalance, tax-aware change, contribution/timeline change, or instrument replacement.
•  Selection only when needed. The shared 16-layer Selection Engine is invoked when an existing instrument genuinely needs replacement.
•  Switching-cost inequality. Source design requires expected benefit to exceed exit load, tax, transaction cost and safety margin; this prevents churn for marginal improvements.
•  Backtesting. The proposed fix is stress-replayed and behaviour hold-ability is considered before presentation.
7.5 Manage and Sandbox
After an approved fix, the source design adds daily tracking, event-driven rebalancing, SIP redesign, goal-drift/life-event re-analysis, report cards and a Scenario Sandbox. Sandbox re-runs the pipeline on a hypothetical post-fix portfolio so the user can compare current versus proposed outcomes before committing. [S3]
Health Check implementation priority
A defensible MVP does not require every advanced sub-engine. The source itself recommends building deterministic XIRR/gap/overlap/cost/risk/score/replacement logic first, then adding forecasting, quantum and behaviour models as data and validation mature.

9.2 FIT ranking versus quantity
FIT_i = sum_l (weight[l, asset_class] * normalized_score[i,l]) subject to hard eligibility/fraud/suitability gates.  Which instrument = FIT ranking. How much = separate sizing/optimization using FIT + correlation + behaviour hold-ability + class bounds + risk/return constraints.

This separation is an important architecture invariant. A top-FIT security can receive a smaller allocation if it is highly correlated with already-selected holdings, violates concentration limits, or is unlikely to be held by the user through normal drawdowns.

9.4 Core quantitative methods
•  Goal mathematics. Required return / SIP solved numerically from future-value constraints; infeasible goals should produce an explicit “unreachable safely” branch.
•  Black-Litterman. Market-implied equilibrium plus controlled views for asset allocation, avoiding unstable raw-return optimisation.
•  Category normalization. Metrics normalized within appropriate peer category before cross-layer aggregation.
•  Risk. Portfolio variance, parametric/historical VaR, CVaR, downside deviation and max drawdown; crisis windows matter.
•  Forecasting. Source proposes Monte Carlo goal probability and forward models with uncertainty; output is a probability, not a guarantee.
•  Optimization. MVO as classical baseline; constrained objective is minimum risk subject to required return and bounds.
•  Tax. Versioned tax-rule tables rather than hard-coded permanent rates.
•  Behaviour. Questionnaire and telemetry can modify risk/hold-ability, but model use must be calibrated, consented and audited.
9.5 Quantum positioning
Classical-first rule
QUBO/QAOA and related quantum paths are experimental. The source design itself requires: build the formulation, solve classically first, benchmark quantum/simulated alternatives, exact-rescore the candidates, and ship only a result that beats the classical baseline. Timeout/noise must return the baseline.

10  NxanceLM Specification
NxanceLM is the human-language intelligence layer around the investment engines. Its latest source taxonomy defines 18+ coordinated mini-engines; this document uses the latest 18+ register. Its analytical scope extends beyond narrow portfolio-specific queries to the broader set of macroeconomic and global-market variables - monetary policy, fiscal policy, trade and geopolitical developments, currency, commodity and energy markets, and other direct or indirect drivers of world-economic conditions - each mapped to its investment relevance. The model is a helper, explainer, retriever and supervised parameter - never the lone portfolio decider. 
Founder-confirmed product framing: NxanceLM should read to the user as two things at once. First, a live-data terminal - each of the 4 Core Layers (Generative Reasoning Processor, Terminal Speed Node, Global Market Radar, Deep Corporate Auditor) gets its own visible, tappable screen surfacing live data directly (an indices, currency, commodities, trade, news and macro-data terminal view), not hidden behind chat. Second, a full open-domain conversational reasoning interface - free-form dialogue and question-answering capability comparable to a general-purpose large language model, but scoped to the complete set of macroeconomic and cross-domain variables that drive global markets, not narrow finance-only queries. This scope includes monetary policy and interest-rate cycles, inflation and employment data, fiscal policy and government spending, geopolitical events and trade-policy shifts, currency and commodity markets, energy and supply-chain conditions, technology and productivity cycles, demographic and labour-market trends, climate and agricultural shocks, and regulatory or sanctions developments - each treated as a direct or indirect, positive or negative driver of global economic conditions and translated into its quantifiable relevance for portfolio and investment decisions. The conversational layer sits on top of the same live data rather than replacing the terminal view, so the user can address it directly for any market, macroeconomic or investment-relevant query. This positions NxanceLM as core infrastructure in its own right, not merely an explanatory add-on to the two portfolio engines.  NXANCE LM is a proprietary, dual-force financial ecosystem that natively fuses a powerful, in-house AI engine with a fully functional, autonomous Live Market Terminal into a single interface.
It does not merely aggregate data feeds. When you seek deep strategic insights, the AI actively drives the research, analyzes complex telemetry, and runs continuous diagnostics (Health Check) alongside asset optimization (Construction). Powered by 18+ core mini-engines and 26 specialized sub-engines, the terminal processes multi-dimensional market inputs to generate deep, plain-language explanations in English or Hindi—all backed by an audited evidence trail instead of opaque, "black-box" scores.
Conversely, when you need pure market analysis, the terminal functions as a complete standalone workspace. Clicking into any section—Market, News, Macro, or Currency—instantly unlocks a full-scale institutional platform where you can independently track, analyze, and view raw, real-time data feeds. The specialized sub-engines run silently in the background, allowing you to click the "Nxance Explain" toggle at any time to instantly overlay plain-language logic and an explicit evidence trail directly onto the live charts.

The workbook includes server/cloud, AI/LLM, larger AI compute, APIs and the engineering/AI/quant team over the runway. The engine blueprints separately describe much lower early runtime infrastructure sketches. Do not compare those as like-for-like: the financial model is total program cash planning; the blueprint sketches are marginal/early infrastructure estimates.
